Efso Radar supplies selective Turkish/global entertainment-news discovery and editorial decision support for Efso Magazin; it does not automatically publish Instagram posts. Python 3.11/3.12 project with modular RSS discovery, multi-source parsing, deduplication/story memory, Gemini integration, Telegram formatting/delivery, SQLite and Turso Hrana v2 repositories, orchestration, encrypted backup primitives and offline staging test runner. ## Historical operational checkpoint — Phase 5B.3G-C Persistent Manifest Foundation (INTEGRATED PR #36, 2026-10-28)

- **Main baseline:** `1530f8340c37e3952b02a8edd56c6b5857845044` (PR #35 integrated).
- **Candidate implementation:** `PersistentManifestStore` and `HermeticTestManifestStore` (`src/efso_radar/staging/persistent_manifest_store.py`), plus extended `OfflineManifestSeal` supporting configured persistent roots (`src/efso_radar/staging/manifest_seal.py`).
- **Remediated safety guarantees enforced (Round 3 review remediation):**
  1. Fail-closed deletion & post-publication preservation (P1-A): manifest deletion via caller-supplied `AuditOutcomeState.CLEAN` is strictly disabled and rejected (`ManifestStoreSecurityError`). If parent directory fsync fails after canonical publication, the manifest is intentionally preserved fail-closed on disk (`ManifestStorePostPublicationError`) for recovery investigation, without deleting the manifest or touching unrelated files.
  2. Publication without overwrite & fallback narrowing (P1-B, P2): `_publish_file_no_overwrite` uses Win32 `MoveFileWithProgressW` without `MOVEFILE_REPLACE_EXISTING` (Windows) and `renameat2(RENAME_NOREPLACE)` / `os.link` (POSIX) to prevent overwriting existing files, late race creations, and dangling symlinks. Fallback from `renameat2` to `os.link` is narrowed strictly to unsupported syscall conditions (`ENOSYS`, `EINVAL`, `EOPNOTSUPP`); real I/O or permission errors (`EIO`, `EPERM`, `EACCES`) fail closed without blind fallback.
  3. Canonical manifest validation & write verification (P1-B, P1-C): strict verification of all 5 synthetic entities against canonical allowlists prior to writing or publishing (rejecting invalid title, modified ownership markers, duplicate entities, or wrong cleanup orders; permits subsequent valid save with the same `run_id`). Write-all loop preventing short writes, `os.fsync()`, pre-publication size and SHA-256 readback check, and post-publication verification.
  4. Trusted test fixture boundary & scoped fixtures (P1 — Round 4): `PYTEST_CURRENT_TEST`, `pytest in sys.modules`, or mutable test mode flags are eliminated as authorization/ownership proof. A dedicated `HermeticTestFixtureScope` context manager/factory carries the trusted scope directly from pytest's `tmp_path`. Candidate fixture validation enforces structural pytest fixture provenance (`pytest-of-*` / `pytest-*` directory tree within system temporary storage), pre-existence, non-root temp location, no symlinks/reparse points, repository/home/system exclusion, and strictly owner-private POSIX mode 0700 permissions. `register_authorized_fixture_root()` is reduced strictly to internal trusted-harness delegation to `HermeticTestFixtureScope`. Fake `PYTEST_CURRENT_TEST` environment variables cannot authorize non-pytest temporary directories.
  5. Threat model clarification (Round 4): Hermetic test mode and fixture scoping are explicitly documented as structural test harness guardrails preventing test stores from accidentally targeting or mutating production, repository, or arbitrary user directories. They do NOT provide a security or privilege-separation boundary against hostile in-process Python code running under the same OS user.
  6. Lockfile ownership & empty content correction (P2 — Round 4): in `_ManifestRunLock._release_lock_if_owned()`, empty content (`content == ""`) is NEVER treated as proof of ownership. Unacquired lock cleanup is permitted only if file descriptor and filesystem identity (inode and device on POSIX and Windows) match the active open descriptor from the acquisition attempt. Foreign lockfiles (both empty and containing foreign tokens) are never unlinked under contention or release attempts across Windows and POSIX.
  7. Consistent post-publication error reporting (P2): any failure after canonical file publication (parent directory fsync, regular file inspection, readback OSError, byte length mismatch, content mismatch, or SHA-256 seal mismatch) consistently raises `ManifestStorePostPublicationError` explicitly stating an uncertain outcome, strictly prohibiting automatic retries, and preserving the canonical manifest file on disk fail-closed for forensic recovery.
  8. Durability limits clarified & neutralized authorization (P1-C, P1-D, P2): documented as a candidate local persistent store foundation with limitations; in-process reopen simulation distinguished from true OS subprocess restart (verified via subprocess) and physical reboot/power-loss durability. Passing `live_authorized=True` is neutralized and rejected; live persistent writes fail closed (`PermissionError`) in this offline foundation.
  9. Concurrency safety: atomic lockfile per `run_id` (`O_CREAT | O_EXCL`) preventing race conditions across concurrent processes and threads.
  10. Read-only reload & seal verification: missing or tampered manifest files fail closed and never grant write permissions.
  11. Hermetic-only offline recovery validation: simulates inspection against in-memory SQLite Schema v6 fixture; never modifies remote Turso, never unlinks manifest, returns `OFFLINE_VALIDATION_PASSED` (never remote `CLEAN`).
  12. Architectural inconsistency documented: noted the contradiction between the historical 80-request cutoff automatic LIVE-08 transition and PR #35's strict monotonic stage sequence, proposing safe policy (no automatic cleanup on early failure; retain manifest fail-closed; separate controlled recovery).
- **Phase 5B.3G-C remains OFFLINE-ONLY:** live execution is NOT enabled. No real Turso connection, no credentials created, and Block Writes remains ON. 43 focused store tests passing (3 skipped on Windows due to unprivileged symlink creation; 46 total), 267 passed across all Phase 5B.3G tests, 768 passed across full hermetic suite, Ruff clean, GitHub Actions CI run 40681304111 clean across all 4 matrix jobs. Ready for independent review.

## Historical operational checkpoint — Phase 5B.3G-C Operator Safeguards (INTEGRATED PR #35, 2026-10-28)

- **Main baseline:** `b6982b499c97cedeb32fadb06df537d3837fd85e` -> integrated at `1530f8340c37e3952b02a8edd56c6b5857845044` (PR #35 merged).
- **Integrated implementation:** `LiveReadyStagingOperator` (`src/efso_radar/staging/live_ready_operator.py`) and `HranaOutboundSecurityBoundary` (`src/efso_radar/staging/hrana_outbound_guard.py`).
- **Safety guarantees enforced:**
  1. Default-deny for live execution: attempts to initialize with real network transports or spoofed transports strictly fail closed (`PermissionError`) by default.
  2. Wire-level authorization & stage sequence gating: mutations at the HTTP wire edge require preflight wire evidence (`_preflight_queries_count >= 10` and 5 baseline collision checks verified on the wire; cannot be caller-self-issued), explicit human window confirmation verified against the active operator instance (`operator._preflight_accepted is True`), and monotonic stage sequence (`LIVE-01` -> preflight completed -> human window confirmed -> `LIVE-02` -> ... -> `LIVE-08`). In the nominal flow, `LIVE-08` is only permissible at stage sequence index 8 after all preceding stages completed; out-of-order stage transitions rejected with `OUT_OF_ORDER_STAGE`. Replay of spent mutations is rejected. Direct-client conditional DELETE before full-row ownership precheck reads on the wire is strictly denied (`OWNERSHIP_PRECHECK_REQUIRED`). Early stage failure halts fail-closed; early cleanup is not permitted as an in-session bypass and remains an open fail-closed recovery requirement. State transitions require sealed manifest SHA-256 validation (no public boolean escalation).
  3. Read-only least privilege: broad table reads replaced by an exact allowlist of SQL templates (`_SYNTHETIC_READ_TEMPLATES`) requiring exact parameter count (1) and manifest PK match. Injection attempts such as `OR 1=1`, join cardinality expansion, subqueries, and extra parameters are strictly blocked with `READ_NOT_ALLOWLISTED`. Preflight queries (`_EXACT_PREFLIGHT_QUERIES`, inspection PRAGMAs) are strictly stage-scoped to `LIVE-01` only and rejected outside `LIVE-01`. All broad, ad-hoc, or post-preflight reads on operational tables remain strictly blocked.
  4. Transport lifecycle & session invalidation: all session exits (nominal run, early halt without human approval, and exceptions) execute in `finally:` to close the HTTP client and permanently invalidate the outbound security boundary (`close_session()`). Any post-session call is blocked with `SESSION_HALTED`.
  5. Strict hard bounds & cleanup reserve protection: request budget ceiling strictly $< 100$ calls (request #100 is blocked); cleanup phase (`set_cleanup_phase()`) is strictly restricted to `LIVE-08` at stage index 8 (`CLEANUP_RESERVE_ESCALATION` denied outside LIVE-08 or before index 8), preserving the 20-request cleanup reserve; session deadline (<120.0s); numeric budget invariants validated fail-closed rejecting booleans (`bool` is an `int` subclass), non-finite floats, negative/zero values, and invalid ranges.
  6. Process-crash recoverable ownership manifest & seal before any mutation (stored in OS tempdir; not machine-reboot durable; reboot resilience remains an open live prerequisite).
  7. Preflight gate (LIVE-01 under Block Writes ON) & explicit Human Approval Window gate before Stage 2 mutations. Incomplete stages or missing human approval strictly prevent `PASSED` status and manifest deletion.
  8. Ambiguous COMMIT outcome handling: produces `UNKNOWN`, stops permanently, no blind retry, retains manifest on disk.
  9. Parameterized conditional DELETE with affected row count verification (`== 1`), pre-deletion wire ownership verification requirement, and independent 3-state audit (`CLEAN/RESIDUAL/UNKNOWN`).
  10. Post-run lockdown recording: offline simulated assertion only (does not prove live cloud dashboard state or token revocation).
  11. Sanitized error reporting with zero SQL, token, or operational secret leakage.
- **Phase 5B.3G-C remains OFFLINE-ONLY:** live execution is NOT enabled. No real Turso connection, no credentials created, and Block Writes remains ON. 60 focused offline operator tests passing.
