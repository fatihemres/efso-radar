## 2026-10-28 Phase 5B.3G-C Persistent Manifest Foundation Checkpoint (Remediated Candidate, Round 4 / Draft PR)

Persistent manifest store foundation implemented under `PersistentManifestStore` and `HermeticTestManifestStore` (`src/efso_radar/staging/persistent_manifest_store.py`) as a candidate local persistence layer with documented platform limitations (Round 4 review remediation):
- Fail-closed deletion & post-publication preservation (P1-A): direct manifest unlinking via caller-supplied CLEAN is strictly disabled and rejected (`ManifestStoreSecurityError`). If parent directory fsync fails after canonical publication, the manifest is preserved fail-closed on disk (`ManifestStorePostPublicationError`) for recovery investigation, without deleting the manifest or touching unrelated files.
- Publication without overwrite & fallback narrowing (P1-B, P2): `_publish_file_no_overwrite` uses Win32 `MoveFileWithProgressW` without `MOVEFILE_REPLACE_EXISTING` (Windows) and `renameat2(RENAME_NOREPLACE)` / `os.link` (POSIX) to prevent overwriting existing files, late race creations, and dangling symlinks. Fallback from `renameat2` to `os.link` is narrowed strictly to unsupported syscall conditions (`ENOSYS`, `EINVAL`, `EOPNOTSUPP`); real I/O or permission errors (`EIO`, `EPERM`, `EACCES`) fail closed without blind fallback.
- Canonical manifest validation & write verification (P1-B, P1-C): strict verification of all 5 synthetic entities against canonical allowlists prior to writing or publishing (rejecting invalid title, modified ownership markers, duplicate entities, or wrong cleanup orders; permits subsequent valid save with the same `run_id`). Complete write-all loop, `os.fsync()`, pre-publication size/SHA-256 readback check, and post-publication verification.
- Trusted test fixture boundary & scoped fixtures (P1 — Round 4): `PYTEST_CURRENT_TEST`, `pytest in sys.modules`, or mutable test mode flags are eliminated as authorization/ownership proof. A dedicated `HermeticTestFixtureScope` context manager/factory carries the trusted scope directly from pytest's `tmp_path`. Candidate fixture validation enforces structural pytest fixture provenance (`pytest-of-*` / `pytest-*` directory tree within system temporary storage), pre-existence, non-root temp location, no symlinks/reparse points, repository/home/system exclusion, and strictly owner-private POSIX mode 0700 permissions. `register_authorized_fixture_root()` is reduced strictly to internal trusted-harness delegation to `HermeticTestFixtureScope`. Fake `PYTEST_CURRENT_TEST` environment variables cannot authorize non-pytest temporary directories.
- Threat model clarification (Round 4): Hermetic test mode and fixture scoping are explicitly documented as structural test harness guardrails preventing test stores from accidentally targeting or mutating production, repository, or arbitrary user directories. They do NOT provide a security or privilege-separation boundary against hostile in-process Python code running under the same OS user.
- Lockfile ownership & empty content correction (P2 — Round 4): in `_ManifestRunLock._release_lock_if_owned()`, empty content (`content == ""`) is NEVER treated as proof of ownership. Unacquired lock cleanup is permitted only if file descriptor and filesystem identity (inode and device on POSIX and Windows) match the active open descriptor from the acquisition attempt. Foreign lockfiles (both empty and containing foreign tokens) are never unlinked under contention or release attempts across Windows and POSIX.
- Consistent post-publication error reporting (P2): any failure after canonical file publication (parent directory fsync, regular file inspection, readback OSError, byte length mismatch, content mismatch, or SHA-256 seal mismatch) consistently raises `ManifestStorePostPublicationError` explicitly stating an uncertain outcome, strictly prohibiting automatic retries, and preserving the canonical manifest file on disk fail-closed for forensic recovery.
- Durability limits clarified & neutralized authorization (P1-C, P1-D, P2): documented as a candidate local persistent store foundation with limitations; in-process reopen simulation distinguished from true OS subprocess restart (verified via subprocess) and physical reboot/power-loss durability. Passing `live_authorized=True` is neutralized and rejected; live persistent writes fail closed (`PermissionError`) in this offline foundation.
- Dedicated hermetic test store adapter (`HermeticTestManifestStore`) for isolated test fixtures.
- Concurrency safety: atomic lockfile per `run_id` (`O_CREAT | O_EXCL`) preventing race conditions across processes and threads.
- Read-only reload and SHA-256 seal verification: missing or tampered manifest files fail closed and never grant write permissions.
- Hermetic-only offline recovery validation: simulates inspection against in-memory SQLite Schema v6 fixture; never modifies remote Turso, never unlinks manifest, returns `OFFLINE_VALIDATION_PASSED` (never remote `CLEAN`).
- Platform storage guarantees: explicit reporting of Windows and Linux storage guarantees and identified blockers (`StoragePlatformGuarantees`).
- Architectural inconsistency documented: noted the contradiction between the historical 80-request cutoff automatic LIVE-08 transition and PR #35's strict monotonic stage sequence, proposing safe policy (no automatic cleanup on early failure; retain manifest fail-closed; separate controlled recovery).
- All live staging operations remain **UNAUTHORIZED**; Block Writes remains ON. 43 focused store tests passing (3 skipped on Windows due to unprivileged symlink creation; 46 total), 267 passed across all Phase 5B.3G tests, 768 passed across full hermetic suite, Ruff clean. Ready for independent review.

## 2026-10-28 Phase 5B.3G-C Live-Ready Operator Preparation Checkpoint (INTEGRATED PR #35)

Operator safeguards integrated into `main` at `1530f8340c37e3952b02a8edd56c6b5857845044` (PR #35 merged).
- Reuses existing hermetic runner, preflight, manifest sealing, and session gate components.
- Enforces strict default-deny for live execution; fails closed immediately on non-hermetic transports (no duck-typing bypasses).
- Outbound boundary wired into transport chain, enforcing wire-level stage sequence and human approval gating: direct client mutations outside active stages or prior to preflight/human approval fail closed immediately. Transitions require source-backed evidence (verified wire preflight requests and operator attestation); public SHA-256 cannot be self-issued to escalate permissions.
- Strict monotonic stage sequence: `LIVE-08` requires all preceding stages completed (stage sequence index 8); early transitions to `LIVE-08` are strictly denied with `OUT_OF_ORDER_STAGE`.
- Wire-level full-row ownership precheck: conditional DELETE statements require verified attribute pre-checks on the wire (`SELECT * FROM {table} WHERE {pk_col} = ?`) and operator verification attestation (`OWNERSHIP_PRECHECK_REQUIRED` if attempted directly or prematurely).
- Early stage failure cleanup policy: in-session early cleanup bypasses are prohibited. Early failures fail closed, preserve the manifest, and mark status `FAILED`; any future early-failure cleanup remains an open, separate fail-closed recovery requirement with cryptographic proof of ownership.
- Read-only least privilege at wire edge: broad operational table queries (`telegram_delivery_records`, etc.) and full table scans strictly rejected (`READ_NOT_ALLOWLISTED`); exact SQL template inventory (`_SYNTHETIC_READ_TEMPLATES`) with exact parameter count (1) and manifest PK match enforced. Preflight queries strictly stage-scoped to LIVE-01 only.
- Strict cleanup reserve protection: `set_cleanup_phase()` strictly restricted to `LIVE-08` at index 8; attempts to escalate cleanup reserve before `LIVE-08` are permanently denied with `CLEANUP_RESERVE_ESCALATION`.
- Full gate workflow: verified LIVE-01 preflight, mandatory human window attestation before write stages, deadline (<120s), budget (<100 requests strictly enforced at wire edge, 20 cleanup reserve), ambiguous COMMIT = UNKNOWN, conditional DELETE (affected == 1), post-run lockdown assertion, and 3-state audit (CLEAN/RESIDUAL/UNKNOWN).
- Transport lifecycle closure: client and security boundary permanently closed/invalidated across all exit paths (nominal run, early exit without human approval, exceptions).
- Unlinking of manifest and PASSED status strictly blocked if human approval, any of the 8 stages, or lockdown assertion is missing or incomplete.
- LOCKDOWN ASSERTION NOTICE: Post-run lockdown recording is an offline simulated assertion only, NOT real cloud dashboard state or token revocation.
- All live staging operations remain **UNAUTHORIZED**; Block Writes remains ON. 60 focused offline operator tests passing.
